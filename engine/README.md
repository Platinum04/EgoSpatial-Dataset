# EgoSpatial engine (v1.0.1)

EgoSpatial is a portable spatial reasoning engine for XR. Given an agent pose and object positions, it answers egocentric and object-relative spatial questions: front, behind, left, right, distance.

- **Geometry is deterministic.** The verified 08A/08B math is ported to a dependency-free Python package. JavaScript (WebXR), C# (Unity / Quest 3S) and Kotlin (Android XR) ports are also provided.
- **Language is neural and optional.** Gemma-2-2b-it can turn free-form questions into a structured query. Its output is validated against the scene, and it never produces the geometric answer itself (see the 08D-7 decision).
- **No guessing.** If a question can't be resolved, the engine returns `status: "unresolved"` with a clarification request.

## Why this architecture (research summary)
In 08C/08D, fine-tuned Gemma-2-2b-it (V4 LoRA) scored 100% on front/behind but **chance on left/right**:

- **Behaviour:** left/right accuracy was 50.75% for V4 and 52.5% for the targeted intervention, on the untouched test set.
- **Output layer:** V4's apparent "right bias" came from bf16 ties near Gemma-2's 30.0 logit softcap. The tie-break favours the lower token id.
- **Hidden states:** layer-wise probes found no linearly decodable left/right signal at any layer of either adapter. The identical method decoded front/behind perfectly.

So the geometry layer is deterministic. See `docs/08D-7_REPORT.md`.

## Measured results (08E, untouched V4 test, n=800)
| System | Overall | Front | Behind | Left | Right |
|---|---:|---:|---:|---:|---:|
| Original V4 (Gemma LoRA) | 75.38% | 100% | 100% | 6.0% | 95.5% |
| 08D intervention LoRA | 76.25% | 100% | 100% | 50.0% | 55.0% |
| Deterministic engine | 100% | 100% | 100% | 100% | 100% |
| Hybrid orchestrator | 100% | 100% | 100% | 100% | 100% |

Language robustness is measured separately, on phrasings never seen in training:

| Set | Hybrid | V4 answering directly |
|---|---:|---:|
| 08E stress (200 questions, 3 phrasings per task), parser v1 | 88.5% | 61.0% |
| 11 fresh set (240 questions, 7 new phrasings), parser v1 | 73.8% | — |
| 11 fresh set, **parser v2 (shipped)** | **87.5%** (egocentric 98.3%, object→object 76.9%) | — |

All hybrid errors come from question parsing; every parsed query gets the exact geometric answer. Neural parsing costs about 1.5 s per question on a T4, against about 0.02 ms for the deterministic template path. The responses include the parsed `query` so a UI can show "interpreting as …" and let the user correct it.

> The V4 test uses the same five question templates as training. 100% therefore measures template parsing plus geometry, not open-language understanding.

## Install and use
```bash
pip install .            # core: zero dependencies
pip install .[neural]    # optional Gemma semantic parser
```
```python
import egospatial as es
state = {"agent": {"position": {"x": 0, "y": 0, "z": 0}, "heading": 90},
         "objects": [{"id": "chair_01", "label": "chair", "position": {"x": 1.2, "y": 0, "z": -0.8}},
                     {"id": "table_01", "label": "table", "position": {"x": -0.5, "y": 0, "z": -1.4}}]}
es.SpatialEngine().ask(state, "Where is the chair_01 relative to me?")["answer"]   # 'front'
es.object_to_agent(es.SpatialState.from_dict(state), "table_01")["direction"]      # 'right'
```
CLI: `egospatial --state scene.json --question "Where is the lamp relative to me?"`
HTTP: `egospatial-server --host 0.0.0.0 --port 8765`, then `POST /ask`, `/evaluate` or `/relations`. See `docs/API.md`.

## Layout
| Path | Contents |
|---|---|
| `egospatial/frames.py` | Canonical frame, heading normalisation, world↔egocentric transforms |
| `egospatial/state.py` | Validated canonical state and deterministic serialisation |
| `egospatial/relations.py` | Deterministic relations: object→agent, object→object (08B-3), reference frame (V4), distance |
| `egospatial/query.py` | Structured `Query` and the template parser |
| `egospatial/orchestrator.py` | `SpatialEngine`: routing, validation, abstention |
| `egospatial/neural.py` | Optional Gemma semantic parser (validated JSON) |
| `egospatial/adapters.py` | V4 dataset, Unity, WebXR / OpenXR / Android XR pose adapters |
| `egospatial/server.py` | Dependency-free HTTP JSON API |
| `ports/js`, `ports/unity`, `ports/android` | Platform ports |
| `examples/webxr` | WebXR demo (simulated mode plus live `immersive-ar` hit-test mode) |
| `tests/` | Python unit and integration tests; `vectors.json` (generated by `tools/make_vectors.py`) |
| `docs/` | Research report, 08D-7 decision, architecture, API, XR integration, datasets, training, reproducibility |

## Known limitations
- Four-way relations only; diagonals tie-break to front/behind, same as 08B. A signed angle is reported for finer use.
- XR runtimes have no true north. Canonical "north" is the platform or session forward axis unless `north_offset_deg` is supplied.
- Neural parsing is the weak link. Parser v2 still mis-parses 28 of 240 fresh questions, mostly the "Looking at X, is Y…" and "Suppose I turn toward X" forms, and gives a confident wrong answer when it does. Constrained decoding or a trained parser is the next step.
- The training and evaluation data are synthetic, with four cardinal directions and two objects per scene. Accuracy on these does not imply general spatial intelligence.
